# Publishing to Hugging Face

*Maintainer instructions. This file is **not** part of either release — the upload roots are `huggingface/model/` and
`huggingface/dataset/`, so only their own contents and cards are pushed.*

Two repositories are staged here. Everything except the checkpoints and the data tables is already written; you add
those and push.

```
huggingface/
  model/      -> a model repository, ready apart from the weights
  dataset/    -> a dataset repository, ready apart from the data tables
```

## Tracked here, versus produced by staging

The scaffold is source code and is in the repository. The weights and data tables are not: they are release artefacts,
and a consumer takes them **from Hugging Face**, not from a git clone.

| in git | created by staging, git-ignored |
|---|---|
| `docs/PUBLISHING.md` (this file, not uploaded) | `model/detector.safetensors` + `model/detector.config.json` |
| `model/handler.py`, `model/inference.py` | `model/context_encoder.safetensors` + its config |
| `model/config.json` — the input contract | `model/compressor.safetensors` + its config |
| `model/requirements.txt` | `model/flow_encoder.safetensors` + its config |
| `model/README.md` — the model card | `dataset/processed/<portion>/<day>/*.parquet` |
| `model/.gitattributes` — LFS rules | `dataset/model/<portion>/<day>/*.parquet` |
| `dataset/README.md` — the dataset card | the generated block inside `dataset/README.md` |
| `dataset/.gitattributes` | |

Note the two files called config: `model/config.json` is the hand-written input contract and is tracked;
`model/<stage>.config.json` is written by the converter from a checkpoint and is not. The ignore rule distinguishes them
by the `<stage>.` prefix.

So after a full staging run the folder looks like this — the tracked files, plus:

```
huggingface/
  model/
    detector.safetensors          detector.config.json        <- the only pair the endpoint needs
    context_encoder.safetensors   context_encoder.config.json
    compressor.safetensors        compressor.config.json
    flow_encoder.safetensors      flow_encoder.config.json
  dataset/
    processed/events/<day>/events.parquet, node_index.parquet
    processed/flow_records/<day>/flow_records.parquet
    processed/side_features/<day>/side_features.parquet
    model/flow_embeddings/<day>/flow_embeddings.parquet + manifest
    model/latents/<day>/event_latents.parquet + manifest
```

Nothing in that list is committed. Re-run staging to rebuild it; the checkpoints and tables it reads are themselves
regenerated by the pipeline.

## What is already here

| file | why it is needed |
|---|---|
| `model/README.md` | the model card. Hugging Face renders it as the front page; the YAML front matter drives discovery |
| `model/config.json` | the input contract: 132 features, flow embedding first then context, and what comes back |
| `model/handler.py` | the Inference Endpoints entry point. The platform imports `EndpointHandler` from here |
| `model/inference.py` | loads `detector.pt` and scores. Self-contained: a model repo must not import this project |
| `model/requirements.txt` | what the endpoint installs — inference needs only torch and numpy |
| `model/.gitattributes` | LFS for `*.safetensors`. **Without this, pushing weights fails or bloats the repo** |
| `dataset/README.md` | the dataset card, with the licence and the column contract |
| `dataset/.gitattributes` | LFS for `*.parquet` |

## Nothing is pasted by hand

`tools/publish/huggingface.py` finds the artefacts, copies them, lays out the directories and rewrites the generated part
of each card. You never place a file in `huggingface/` yourself.

| you run | the tool does |
|---|---|
| `--what model` | finds the newest checkpoint for each of the four stages, converts it to safetensors, verifies every tensor is bit-identical, deletes the `.pt`, writes `<stage>.config.json` |
| `--what dataset` | finds the parquet tables, copies them to `<set>/<portion>/<day>/`, carries each manifest along, rewrites the card's `configs:` block and inventory |

The only prerequisite is that the artefacts exist — that is, the pipeline has run. `--dry-run` reports what it would
stage, with sizes, and copies nothing.

## What must exist first

**Model** — four trained stages. Staging converts each to **safetensors plus a config**, and deletes the pickle:

| stage | produced by | published as |
|---|---|---|
| detector | `models.detector --save`, then `models.evaluation.thresholds --write` for the operating point | `detector.safetensors` + `detector.config.json` |
| context encoder | `models.context_encoder --out` | `context_encoder.safetensors` + config |
| compressor | `models.compressor --out` | `compressor.safetensors` + config |
| flow encoder | `models.flow_encoder --save-scores` | `flow_encoder.safetensors` + config |

One command does all of it:

```bash
uv run python tools/publish/huggingface.py --what model --user <account>
```

For each of the four stages it finds the newest checkpoint, copies it, converts it to safetensors, **verifies every
tensor is bit-identical** to the original, writes `<stage>.config.json`, and deletes the `.pt`. There is no second step:
conversion is not something you run afterwards. Only the detector is needed for the endpoint to serve; the other three
are what a consumer needs to reproduce the features it expects.

Why not publish `.pt`: `torch.load` unpickles, so loading a downloaded checkpoint can execute code. safetensors cannot.
The trade is that non-tensor fields — class order, widths, thresholds — move to a sibling `config.json`, so each stage is
two files and both must be uploaded.

### Converting one checkpoint on its own

`tools/publish/to_safetensors.py` is the converter that staging calls. **You should not normally need to run it
directly.** It exists for three cases the staging search does not cover: a checkpoint outside the directories
`--what model` looks in, re-converting after editing a config by hand, and converting a single stage to share somewhere
other than Hugging Face.

```bash
uv run python tools/publish/to_safetensors.py <checkpoint>.pt huggingface/model/detector   # one file
uv run python tools/publish/to_safetensors.py --stage huggingface/model                    # every .pt in a directory
```

Both verify the result against the source before removing anything.

**Dataset** — two sets, staged independently so a consumer can take one portion without the rest:

| set | portion | config a consumer loads | what it is |
|---|---|---|---|
| `processed` | `events` | `processed_events` | the labelled event stream; model-agnostic |
| `processed` | `flow_records` | `processed_flow_records` | CICFlowMeter's 69 columns per event |
| `processed` | `side_features` | `processed_side_features` | per-event request/response features |
| `model` | `flow_embeddings` | `model_flow_embeddings` | Block 7's per-flow embedding (the largest portion) |
| `model` | `latents` | `model_latents` | Block 9's `z` + `recon_error` — what the world model reads |

```bash
# everything found, reported first
uv run python tools/publish/huggingface.py --what dataset --dry-run --user <account>

# just the model-consumable latents, one day
uv run python tools/publish/huggingface.py --what dataset --include latents --days Friday-02-03-2018 --user <account>

# the whole model-agnostic set
uv run python tools/publish/huggingface.py --what dataset --include processed --user <account>
```

Each day becomes a Hugging Face **split**, so a consumer can fetch one day rather than all five. The card's YAML front
matter and inventory table are **generated from what was actually staged** — a config pointing at absent files would
fail in the consumer's notebook, which is the worst place to discover it. Everything below the `END GENERATED` marker is
prose and is never touched by the tool.

Full inventory on this machine, for reference: `processed` is about 2.8 GB across five days, `model` about 12 GB
(`flow_embeddings` 6.1 GB, `latents` 5.7 GB). Stage selectively.

## Push

```bash
huggingface-cli login
huggingface-cli upload <account>/netwatch-flow-cascade    huggingface/model   . --repo-type model
huggingface-cli upload <account>/netwatch-ids2018-events  huggingface/dataset . --repo-type dataset --private
```

## Before making either public

The **code** here is MIT. The **data** is not: CSE-CIC-IDS2018 comes from the Canadian Institute for Cybersecurity under
its own terms, which require attribution and govern redistribution, and every event stream, embedding and latent here is
a derived work of it. The dataset card is marked `gated: true` for that reason. Read those terms first.

The model card states what the system does **not** claim — no cross-day or unseen-attacker generalisation, and no
anticipation claim in seconds. Keep those in place; they are the difference between a defensible release and an
overclaim.
