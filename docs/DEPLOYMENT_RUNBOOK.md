# Deployment runbook — training, validation, and the statistics you set

Written 2026-09-20. Every command was read off the actual `--help` of the file it names, and every number is either
measured or marked *unmeasured*. Where a command was run to check it works, the wall time is given.

**Everything under `data/` is disposable.** Checkpoints, latents, embeddings, score blobs, thresholds and result CSVs
are all regenerated by the next longer run on more days — that is expected, and nothing in the system should ever
depend on a specific file surviving. What is *not* disposable: the contracts in `docs/*.json`, the settings in §6, and
the reasoning in §7. When you re-run on ten days, expect every number in §6.1 to move and re-derive the operating
point rather than carrying the old threshold forward. **A threshold from a previous fit is not stale, it is void** —
it is a point on a score scale that no longer exists.

## IMPORTANT — unmeasured and unrecoverable things

Four items that are **not bugs and not blockers**, but each will cost someone a day if it is discovered rather than
read. None is fixable by more training.

### 1. The reorder-buffer delay is unmeasured

`ReorderBuffer(delay)` holds each event until no earlier-observed event can still arrive. `delay` must exceed the
worst-case spread between a packet arriving at the sensor and its event's `t_obs`. **No one has measured that spread on
live capture.** The default of 50 ms is a placeholder.

Release too early and the context encoder receives an out-of-order stream. Nothing raises: link memory updates in the
wrong order, the neighbourhood contains the wrong events, and any "three consecutive events" run test silently changes
its answer. Measure it against real sensor timing before trusting a live alert rate.

### 2. The normalisation behind the existing flow embeddings exists nowhere on disk

`models/data/inputs.py::normalise` fits its statistics on the sampled training rows of one run. Until 2026-09-21 the
Block 7 checkpoint stored only weights, so the statistics behind every file currently in `data/flow_embeddings/` are
gone. They are **deterministically recomputable** — the sampling RNG is seeded — but only by re-running with the
identical `--fit-day`, `--sample` and `--seed`, against unchanged input data.

Going forward the checkpoint stores them (`format: block7-encoder-v1`) and the export manifest records a
`normalisation_sha256`. Two exports whose fingerprints differ are on different input scales and must not be compared or
mixed, however similar their configuration looks. A checkpoint saved before this carries none, and `--load-from` warns.

### 3. Node ids are per day, so a saved state table is not portable

`ingest/build/events.py` numbers hosts by first appearance **within one day**. Slot *i* in the world model's state table is a
different host on a different day, which is why `load_world_model` defaults to `restore_state=False`. Restoring a table
against another stream does not fail — it silently attributes one host's history to another.

A live deployment needs its own stable ip → id map. `models/serving/graph.py::NodeRegistry` is the mechanism, and
**someone must own that file and its backup**: losing it renumbers every host, after which the state table points at the
wrong hosts and link memory starts cold for every link at once.

### 4. `fp_at_target_oracle` is named that for a reason

Reaching a target recall requires knowing where the attack scores lie, so the threshold behind that column is chosen
using test labels. No live system can reproduce it. It is valid only for ranking two arms against each other on
identical rows, and never as an achievable operating point. Quote the budget → quantile → realised-FPR path
(`models/evaluation/thresholds.py`), which never looks at a label.

## 1. Serving artefacts — what a live process loads

Until 2026-09-20 training produced nothing loadable: the supervised head, its feature scaler and every threshold were
discarded at process exit, and Block 10 had no checkpoint at all. All three are now written.

| artefact | written by | contains |
|---|---|---|
| Block 7 packet encoder | `models.flow_encoder --save-scores DIR` | weights, per `DIR/<stem>.pt` |
| Record encoder (optional) | `models.context_encoder.records --train-encoder PATH` | weights, frozen before Block 8 sees it |
| Block 8 context encoder | `models.context_encoder --out DIR` | `DIR/best.pt`, incl. the `capacity` it was fitted with |
| Block 9 autoencoder | `models.compressor --out DIR` | `DIR/best.pt`, incl. `d_z` and `window` |
| **Supervised head** (main line) | `models.detector --save PATH` | head weights, **feature mean/std**, family names, budget thresholds, and `serve_threshold` |
| **Score distributions** | `models.detector --save-scores PATH` | calibration-benign + test scores, for threshold sweeps |
| **Block 10 world model** | `models.world_model_proxy --save PATH` | dynamics weights, **latent scaler**, warm per-key state table, per-horizon thresholds |
| **The chosen threshold** | `models/evaluation/thresholds.py --write <head checkpoint>` | into that checkpoint's `serve_threshold` |

Two scalers are as much part of their model as the weights. `class_scores` standardises with the training `mean`/`std`;
`run()` standardises `z` with the train split's statistics. A process that reloads weights without them scores on a
different scale and **every threshold is meaningless** — so both travel inside the checkpoint.

The emitter and recalibrator are code, not artefacts: `models/serving/emitter.py`, §5.

**One remaining serving gap, needing no training:** the Block 10 state table is indexed by node ids, and node ids are
**per day** (`data/events/<day>/node_index.parquet` is built one day at a time). Slot *i* is a different host on a
different day, so `load_world_model(..., restore_state=True)` is only valid for the stream it was saved from. A live
deployment needs its own stable ip → id map; until then it must start from a cleared table.

### 3.4 Block 7 — the servable fit
Every Block 7 checkpoint on disk is *leave-one-day-out*, i.e. has never seen one of your days. For serving, fit on all
of them:
```
uv run python -m models.flow_encoder \
  --fit-day <all days> --cross-day Friday-02-03-2018 \
  --side split --budget-ms 10 --epochs 30 --patience 5 \
  --save-scores data/model_cache/block7_serve \
  --export data/flow_embeddings/split_serve \
  --results-csv data/model_cache/results/block7_serve.csv
```
`--side split` is what Block 8 and the classifier read. `--export-days` defaults to the fit days. **Whichever day you
pass as `--cross-day` is also a fit day here, so this run's scores are contaminated and must not be quoted** — the
checkpoint and the export are the deliverable. Keep the leave-one-day-out runs for every reported Block 7 number.
`--budget-ms 10` is the design's observation budget; changing it invalidates everything downstream.

### 3.5 Block 8 — context encoder
```
uv run python -m models.context_encoder --arm split --days <all days> \
  --out data/model_cache/block8_10d \
  --epochs 10 --patience 2 --batch-size 200 --lr 1e-3 --seed 0 \
  --capacity 0.25
```
Omit `--events`: that flag is the slice proxy and this is the full run. Add `--flow-records --flow-messages
--record-encoder data/model_cache/record_encoder.pt` only if §3.3 covered every day. Early fusion (the union merge) is
settled — all four reference papers back it over concat and it measured better here — and there is deliberately no
flag to select late fusion.

`--capacity 0.25` caps link memory and recycles least-recently-used slots, which is what a live stream requires. The
value is stored in the checkpoint, so Block 9 and `--block8` honour it with no extra flag. *Measured: 1,000 distinct
links through a 250-slot table produced 750 evictions; a `--capacity 0.25` fit on Thursday-15 reached validation link
PR-AUC 0.9820 (1 epoch, 150k events, 1 m 47 s).*

### 3.8 The supervised arm — the main line
```
uv run python -m models.detector --days <all days> \
  --block8 data/model_cache/block8_10d/best.pt \
  --save data/model_cache/serve/head.pt \
  --save-scores data/model_cache/serve/scores.pt \
  --out data/model_cache/results/supervised_10d.csv --seed 0
```
`--save`/`--save-scores` are suffixed per day automatically (`head_<day>.pt`), so a ten-day run leaves ten checkpoints
rather than overwriting one. `--block8` is **not optional for the real system**: it is the only path by which link
memory, the neighbourhood and the flow messages reach the supervised arm. `--block9 <ckpt>` adds Block 9's
reconstruction error as a second condition — **measured and rejected**, it cost recall without buying FPR. Repeat with
`--seed 1` and `--seed 2`; three seeds is the standing rule since a non-determinism bug once masqueraded as ~5 pt of
seed variance.

*Verified end to end: 3M-event Bot slice, seed 0, `--block8 f_norec_s1` — 3 m 57 s, head and scores both written.*

### 3.9 Block 10 — world model, per day
`--latents` takes one directory per arm and each export directory is one day, so run it per day:

## 4. Choosing and committing the threshold

Deliberately a separate step, in a separate file, because it is a judgement about acceptable alert volume rather than
an output of the fit — and because it must be testable on its own.

```
# look at the whole tradeoff (seconds, no GPU, no refit)
uv run python -m models.evaluation.thresholds --scores data/model_cache/serve/scores_<day>.pt \
  --out data/model_cache/results/thresholds_<day>.csv

# then commit the cheapest point that still meets a recall floor
uv run python -m models.evaluation.thresholds --scores data/model_cache/serve/scores_<day>.pt \
  --recall-floor 0.995 --write data/model_cache/serve/head_<day>.pt
```

**Where the number goes:** into `serve_threshold` inside the head checkpoint. Nothing else writes that field, and a
serving process reads only that. It is stored with the weights on purpose — a threshold in a separate config file
drifts away from the model it belongs to.

`--write` refuses to run without `--recall-floor`, so a committed threshold is always one that met a stated floor.

Real output, Bot day 3M slice, seed 0 (558,504 benign test rows over 0.72 h):

| 0.3% | 0.017449 | 0.336% | 1.12× | 1.0000 | 0.897 | 2,626 | 1,655 |
| 0.1% | 0.062141 | 0.117% | 1.17× | 1.0000 | 0.962 | 916 | 689 |

means the calibration sample has run out of resolution.

## 5. The emitter — score to something a human reads

`models/serving/emitter.py`. Three stages, in this order, all incremental:

1. **Threshold** — from `serve_threshold`.
2. **Persistence** — `persist=3`: three consecutive events above threshold on the same key. The counter resets on
   *any* event below threshold, which makes it a run test rather than a count. *Measured: halves false alarms
   (58 → 30) at zero cost to early recall.*
3. **Incident de-duplication** — `gap=60.0`: alerts on one key with no quiet gap longer than 60 s are one incident.
   *Measured: 30 alerts → 8 incidents.*

Together: 8,544 alerts/hour → **41.9 alerts/hour, 11.2 incidents/hour**.

**Those three figures are the world-model arm**, measured on the Bot slice keyed on the sender — `recall_early` and
campaign onsets, the costs quoted above, exist only there. The detection arm's equivalent is in §16: 22,708/hour →
**29.4 incidents/hour**. The *mechanisms* are arm-agnostic, so the multipliers should hold for either; the *absolute
rates* depend on the score distribution and the threshold and do not transfer.

```python
from models.serving.emitter import AlertEmitter, Recalibrator
emitter = AlertEmitter(threshold, persist=3, gap=60.0)
for incident in emitter.push_batch(keys, scores, times):   # push order IS availability order
    publish(incident)
emitter.rates(hours)        # events, alerts, incidents + per-hour rates, for GET /health
```

**Push order is availability order.** A run of three means three *consecutive* events on that key, so a batch sorted by
anything else changes the answer. The emitter prunes keys whose incident closed more than one gap ago so the table
stays bounded.

**Recalibration.** `Recalibrator(budget)` keeps a reservoir sample spanning everything seen *plus* a FIFO of the most
recent rows, and reads the quantile off their union. A threshold read from one contiguous recent stretch overshot its
budget **six-fold** on another segment of the same day, which is why a recent window alone is not enough. Feed it
scores of rows that did not alert; call `drifted(realised_rate)` and recalibrate when it returns true (outside 3× of
budget either way — offline the rule never left 1.0–2.4×).

## 8. What must not be claimed

1. **Slice numbers are not absolute numbers.** `attack_slice` (`models/context_encoder/data.py:147`) centres on the attack
   span. On the Bot day it **starts 3,446 s after the first Bot attack and contains 0 of the day's 1,239,249
   pre-attack rows**; its own docstring says it is "for comparing arms, not for absolute numbers". Every
   alarms-per-hour figure in §4 is slice-conditioned. A slice narrower than ~3M on the Bot day has no test rows at
   all — `run_day` now says so instead of failing with an IndexError.

2. **Anticipation cannot be scored with the current split.** `segment_split` (`models/data/splits.py:76`) cuts
   60/10/30 *inside every attack window and benign stretch separately*, deliberately, so every split gets attack rows.
   The splits therefore interleave in wall-clock time: **1,677,561 of 1,680,628 Bot-day test benign rows occur before
   the latest train attack**. A "will this host attack later" score is contaminated. The lead is real — Bot has 2,568
   test rows across 10 hosts whose first attack is still ahead, ~44 min median; Infiltration 10,865 across 10 hosts —
   but only cross-day transfer or `tools/world_model/leave_attackers_out.py` can score it.

3. **`fp_at_target` is an oracle.** It picks its threshold using test attack scores. The old headline "1–2 false
   alarms at 99% recall" came from it and is invalid. Quote only the budget → quantile → realised-FPR path in §4.

Also measured and rejected, so do not enable: Block 9's gate (`--block9`), per-key normalisation, receiver keying,
late fusion. And `--lead-steps`' help text still cites "measured lead 2.02 s", which came from the slice and is void
per point 1.

## 10. Building the graph from live traffic

Every graph structure the trained cascade reads is built offline by a whole-array pass over a finished day, and **none
of it can serve**. `models/serving/graph.py` is the online counterpart, verified against the offline code:

| offline | why it cannot serve | online |
|---|---|---|
| `ingest.build.events._build_node_index` | node ids are `np.arange` over first appearance **within one day**, so the same host is a different id tomorrow | `NodeRegistry` |
| `models.context_encoder.model.LinkIds` | sorts the whole stream's pairs; a link id is an index into that table, and link id **is** the memory slot | `LinkRegistry` |
| `models.context_encoder.stream.NeighbourIndex` | `np.lexsort` over the entire stream, queried by absolute stream position | `OnlineNeighbours` |
| `ingest.build.events._time_since_last_seen` | groupby-diff over the whole day, for `dt_src`/`dt_dst` | `LastSeen` |
| `models.context_encoder.stream.availability_order` | sorts the finished day by `(t_obs, event_id)` | `ReorderBuffer` |

`OnlineNeighbours` reproduces `recent_neighbours` **event for event** over a 400-event stream (its `demo()` asserts
this). Getting there corrected two wrong assumptions of mine, both of which would have silently changed Block 8's
input:

1. The two roles are **separate tables**. An event's neighbourhood is "events where my sender also sent" plus "events
   where my receiver also received" — never "anything either endpoint touched". Conflating them invents neighbours.
2. An event's **own link is excluded entirely**, at any recency — not merely when the run is ongoing. Link memory
   already carries that link's history, so the neighbourhood exists to add the *other* context.

**The registries must be persisted.** `NodeRegistry.save/load` and `LinkRegistry.save/load` exist because node and link
ids are *identity*: lose them and a restarted process renumbers every host, the world model's state table then points at
the wrong hosts, and link memory starts cold for every link at once. An evicted host that returns is given a **fresh**
id rather than inheriting a stranger's, because silent id reuse corrupts state instead of merely losing it.

`ReorderBuffer(delay)` is the one knob needing a real measurement: `delay` must exceed the worst-case spread between a
packet arriving and its event's `t_obs`. Release too early and Block 8 sees an out-of-order stream, which changes link
memory, the neighbourhood, and any "three consecutive events" run test — with no error anywhere.

### Still missing for a live system

Checkpoints saved before this carry no stats, so `--load-from` recomputes them from that run's `--sample`/`--seed` and warns. Existing exports in `data/flow_embeddings/` were produced with stats that exist nowhere on disk — reproducible only by re-running with identical flags |

## 11. Evaluation — the one command that shows every metric

Before this, metrics lived across a dozen experiment scripts and `tools/collect_final.py` only knew how to gather the
seven final experiments *by number*. Nothing produced the whole picture for a given trained model.

```
uv run python -m models.evaluation --scores data/model_cache/serve/scores_<day>.pt \
  --out data/model_cache/results/evaluation_<day>
```

Four tables, in this order:

1. **Ranking and calibration**, threshold-free — tied-rank PR-AUC, Brier, ECE. Ties are collapsed because at a 10 ms
   budget most of a flood's rows share an identical input vector and therefore an identical score with some benign row;
   ranking those by array position would invent a separation the model never produced.
2. **Operating points** — budget → threshold → realised FPR, recall, precision, alarms/hour, incidents/hour.
3. **The emission funnel** — events → above threshold → after persist-3 → incidents, run through the real
   `AlertEmitter` rather than a reimplementation.
4. **By observation population** — `early_observation` against `completed_before_budget`, never pooled: only the first
   carries any lead-time claim.

Measured on the Bot day, **detection arm** (3M slice, seed 0, 574,893 test rows over 0.72 h), in ~4 s on the GPU. The
world model's equivalent numbers are in §5 and are not interchangeable with these:

| metric | value |
|---|---|
| PR-AUC (tied) | 0.999973 |
| Brier / ECE | 0.000157 / 0.000525 |
| at threshold 0.9793 | recall 0.9906, 6 false alarms, **8.4 false alarms/hour** |
| emission funnel | 16,241 above threshold → 15,409 after persist-3 → **21 incidents** (29.4/hour) |
| coverage | all 10 attacking hosts alerted; all 16,389 attack events on an alerting host |

The funnel line is the one to show an operator: raw alerting is 22,708/hour, what a human actually sees is **29.4
incidents/hour**.

## 12. Explainability

The problem statement asks for it, and the context encoder already computed the answer and discarded it: an attention
distribution over each event's neighbourhood, thrown away by `need_weights=False`.

```
uv run python -m models.explanation --block8 data/model_cache/block8_10d/best.pt \
  --day Friday-02-03-2018 --family Bot --events 3000000 --attacks-only --explain 25
```

Two complementary answers per alert:

- **"Why this host?"** — the attention weights over up to 20 neighbours (the latest event per distinct peer of each
  endpoint), reported with each neighbour's age, role and label. This is a real activation of the trained model, not a
  post-hoc surrogate.
- **"Was it the flow or its context?"** — `input_attribution` does gradient×input over the detector's 132-wide input and
  sums the 32 flow-embedding columns against the 100 context columns, signed, so a span can argue *for* benign.

Two things this is careful about. An event with an empty neighbourhood is made to attend a zeroed dummy slot, so its
weights are an artefact — `valid` rides alongside and `top_neighbours` reports `-1` rather than presenting a padded slot
as evidence. And capture is opt-in (`encoder.explain = True`), verified to leave the encoding **bit-identical**, so
turning explainability on cannot change a verdict. Attribution is a local linearisation, not a causal claim.

## 13. Backend configuration, and what torch.compile is actually for

`models/runtime.py` sets the backend flags. **Call `configure()` once at start-up**; the detector, the world-model
proxy and the evaluation already do.

```python
from models.runtime import configure
configure()                 # reproducible: the default
configure(fast=True)        # cuDNN autotuning + TF32
```

| flag | default | why |
|---|---|---|
| `cudnn.benchmark` | **off** | It autotunes by timing algorithms per input shape. Fast for fixed shapes, counterproductive for varying ones, and the algorithm chosen can differ between runs — different algorithms accumulate in a different order, so results move in the last bits. |
| `cudnn.deterministic` | **on** | The reproducible kernels. |
| TF32 | **off** | 10-bit mantissa through tensor cores: typically 2–8× faster on float32 matmuls, and it changes results. Acceptable while training, not while measuring a threshold to six significant figures. |
| `use_deterministic_algorithms` | on, `warn_only=True` | A kernel with no deterministic implementation warns and names itself instead of leaving a silent source of variance. |

Given this project's history with nondeterminism, the stable path is the default and speed is opt-in via `--fast`.

### torch.compile — measured, and not recommended here

One correction worth stating plainly: **`torch.compile` is a speed optimisation, not a memory one.** It traces the
graph, fuses kernels and removes Python overhead, and it charges a one-off compile cost of seconds. Any memory benefit
is a side effect of fusion, not its purpose.

Two measurements decide it for the evaluation path:

1. **It cannot run in this environment.** `cc`, `gcc`, `g++` and `clang` are all absent, and Inductor shells out to a
   host compiler. The call fails with `InductorError: Failed to find C compiler` — at run time, after work has started.
   `models.runtime.compiler_available()` checks for this, and `maybe_compile()` falls back to eager with a message
   rather than dying mid-run.
2. **It would target the wrong 3%.** Profiling the evaluation showed 125 ms total, of which **87 ms was
   `emission_funnel`** — 66 ms inside `push_batch` as 21,337 sequential `_step` calls, plus **28 ms of `.tolist()`
   transfers**. The fusible tensor work was **1.6 ms**. A graph compiler cannot absorb a stateful per-key Python loop.

What did help was fixing the measured bottleneck: `push_batch` now transfers **only the rows that clear the threshold**
instead of the whole batch, which took the evaluation from **105 ms to 63.7 ms (1.65×)** with identical output.

`--compile` remains available on `models.evaluation` for completeness, and will work if a compiler is installed. Where
it would genuinely pay is a training loop running thousands of small ops per chunk — the world-model proxy's step is the
candidate — but that is unmeasured here, because it cannot be measured without a compiler.

### GPU use elsewhere

| path | state |
|---|---|
| Threshold sweep (`models/evaluation/thresholds.py`) | all budgets in one `torch.quantile` plus one broadcast compare: **83.8 ms → 14.0 ms on GPU, 6.0×**, metrics identical to the CPU path |
| Evaluation (`models.evaluation`) | torch throughout, GPU by default, 63.7 ms for a full report |
| Emitter thresholding | one kernel over the batch; only firing rows reach Python |
| Graph registries | `torch.unique` collapses a batch to distinct keys before any dictionary work |

Deliberately left on the CPU: the per-key run counter, the ip → id map and the reorder buffer. These are sequential
dictionary and heap operations on a few hundred rows, where moving to tensors is slower, not faster.

## 14. Splits: use `stratified`, and check coverage before training

The split is the one setting that can invalidate a whole run silently, so check it first:

```bash
uv run python -m models.data.splits                    # every ingested day, every family
uv run python -m models.data.splits --out data/model_cache/results/splits.csv
```

It exits non-zero if any family is missing a split. Measured across the five ingested days:

| mode | result |
|---|---|
| `stratified` | **complete** — every family reaches train, val and test |
| `segment` | 2 family/day pairs missing validation entirely |
| `chronological` | **all 9** family/day pairs missing a split |

### What went wrong with `segment`, precisely

It cuts each segment at a **fraction of the segment's clock**, which starves a family in two ways:

1. **A short window loses validation.** The val band is 10% of the segment, so a segment under 1,200 s has a band
   narrower than the 120 s embargo and nothing survives. Friday-23's 780 s window left SQL Injection with **0**
   validation rows.
2. **A burst that ends early lands wholly in train.** DoS-Hulk's **1,843,441 rows all fall in the first 802 s of a
   2,040 s window**, so the cut at 60% of the clock put every one of them in train and left val and test with none.

A family missing from a split is invisible in every metric computed afterwards, and nothing else in the pipeline
notices. That is why the report exists and why it returns an exit code.

`stratified_split` cuts by **rank within each family's own rows**, so the fractions apply to the family's events rather
than to the clock. DoS-Hulk's validation went from 0 to 184,344 rows, SQL Injection's from 0 to 7, Infiltration's from
59 to 3,600. Ordering is still chronological within a family and within a segment.

### `chronological` is measured, not recommended

It is the only mode that does not interleave in wall-clock time, which is what anticipation needs — and on every single
day the 60% boundary falls after the last attack window, so **every attack lands in train and test has none to score**.
It is provided to be measured against. The only honest route to an anticipation number is a **cross-day holdout**.

## 15. Monitoring, schedules and resuming

All three trainers take the same flags, from `models/training.py`:

```bash
uv run python -m models.context_encoder ... \
    --tensorboard data/model_cache/tb --run-name ctx_5d \
    --resume data/model_cache/ctx_5d_resume.pt
tensorboard --logdir data/model_cache/tb
```

| flag | what it does |
|---|---|
| `--tensorboard DIR` | scalars per epoch. Omitted disables it entirely; a missing TensorBoard never stops a run |
| `--run-name` | subdirectory, so runs are comparable in one board |
| `--resume FILE` | written after **every** epoch, including the optimiser and schedule state. A missing file starts fresh, so it is safe to pass on a first run |
| `--lr-schedule` | `none` (default), `cosine`, `plateau` |

Two scopes are logged, deliberately distinct: `epoch/` is the number early stopping reads, `day/<stage>/` is the
per-day detail behind it. Writing both under one tag put two different values on the same series.

**Resume restores the optimiser, not just the weights.** Adam's moments are part of where a run had got to; resuming
with a fresh optimiser is a different trajectory, not a continuation. The resume file is separate from `best.pt` because
they answer different questions — the best checkpoint is the deliverable and must not be overwritten by a worse later
epoch.

### On the learning-rate schedule

**The default is `none`, and that is deliberate.** Every measured number in this repository was produced with a constant
rate and early stopping over at most ten epochs. Switching the default would invalidate all of them while claiming an
improvement nobody has measured.

My honest expectation is that it matters little here: these are small models that early-stop long before a schedule has
room to work, and `plateau` in particular interacts with early stopping — a plateau patience at or above the
early-stopping patience means the run ends before the rate is ever reduced. `cosine` is the safer of the two if you want
one. Verified working: a 2-epoch run annealed 1e-3 → 5e-4. Measure before believing a gain.

## 16. Per-stage evaluation

An end-to-end number says the cascade works. It does not say **which stage moved**, and in a frozen cascade that is the
question that matters: every later stage inherits whatever the earlier one produced.

```bash
uv run python -m models.evaluation.blocks --days <days> --latents data/latents/<run>/<day>
```

Measured on Thursday-15:

| stage | width | effective rank | separability | attack/benign error |
|---|---|---|---|---|
| flow encoder | 32 | 22.9 (72%) | 1.03 | 35.1× (aggregates), 44.8× (packets) |
| compressor | 32 | 20.0 (63%) | **2.17** | 19.2× |

Two columns to read. **`effective_rank`** is how many directions the output actually uses: a stage can hold a healthy
loss while collapsing to a handful, at which point the next stage is fitted on far less than its width suggests.
**`ratio`** is attack error over benign error — at or below 1 the reconstruction carries no signal, whatever its
absolute value. The reconstruction errors are reported **per target**, because the export's own manifest warns against
combining them without standardising first.

The compressor's separability (2.17) exceeding the flow encoder's (1.03) is the context encoder earning its place.

## 17. Serving the chain without files

Training writes a file per stage and the next stage reads it back. That is right for training — each stage is fitted
once and its output reused by many runs — and wrong for serving.

```python
from models.serving.cascade import Cascade

cascade = Cascade("data/model_cache/serve", capacity=0.25)   # one load
cascade.reset(links=n_links)                                  # one stream
verdict = cascade.decide(features, keys=senders, times=t_obs)  # probabilities + incidents
```

Every stage is loaded once, frozen (`eval()` and `requires_grad_(False)`, so a serving process cannot leak a graph
under load), and kept on one device.

Two properties worth knowing:

- **The context encoder is stateful; the others are not.** Link memory and the neighbourhood accumulate across calls,
  which is the point of it, and it also means an instance belongs to **one stream**. `reset()` starts another; reusing
  an instance without it mixes two hosts' histories.
- **The emitter is kept across calls, per family.** Persistence is a run of consecutive events and an incident spans
  them, so rebuilding it per batch would reset both and inflate the incident count. The self-check covers exactly this:
  two events in one call plus a third in the next must open one incident.

`z` alone is refused as detector input, with a message saying why: the detector reads the flow embedding beside the
context vector, and `z` is the world model's input. A wrong-width tensor that happened to broadcast would score every
event against meaningless weights.
